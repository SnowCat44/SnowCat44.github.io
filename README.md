# 운영 매뉴얼

해당 저장소(repositories)는 [SnowCat44](https://github.com/SnowCat44)가 직접 작성하는 학술 노트 파일이다. 모든 페이지의 표기 방식과 구성 규칙은 다음 내용을 따른다.

### 이 문서의 표기

- `<…>`는 실제 값으로 바꿔 쓰는 자리를 뜻한다.
- "한다", "하지 않는다"로 끝나는 문장은 반드시 지키는 규칙이다.
- **(빌드 검사)** 표시가 있는 규칙은 어기면 빌드가 실패하므로 배포되지 않는다. 표시가 없는 규칙은 사람이 지켜야 한다.
- **(제안)** 표시가 있는 규칙은 아직 확정되지 않은 것이다.

### 하위 구성 단위

| 단위 | 영문 | 설명 |
|------|------|------|
| 편 | Part | 전체를 크게 몇 가지 커다란 영역이나 주제로 나눈 최상위 단위 |
| 부 | Part/Division | 편의 아래이거나 편과 혼용되어 쓰이며, 특정 주제군을 묶어주는 단위 |
| 장 | Chapter | 내용을 구체적인 이야기나 주제별로 나누는 가장 보편적인 기본 단위 |
| 절 | Section | 장 내부에서 소주제나 세부 내용을 다시 나누는 하위 단위 |
| 항 | Subsection | 절보다 더 잘게 세부 항목이나 단락을 구분할 때 쓰이는 단위 |

## 1. 기본 원칙

1. 저장소에는 공개되어도 되는 파일만 올린다. 저장소도 사이트도 공개 상태다.
2. 모든 사실 주장에는 출처를 단다. 출처가 없는 내용은 직접 작성했거나 추론한 것임을 밝힌다.
3. 한 번 정한 주소는 바꾸지 않는다. 주소란 폴더와 파일의 경로를 말한다.
4. 하나의 지식은 한 곳에만 쓰고, 다른 곳에서는 링크만 한다.
5. 빌드 경고를 무시하지 않는다. 경고가 하나라도 있으면 배포되지 않도록 설정되어 있다.

---

## 2. 사이트가 만들어지는 과정

1. `docs/` 안의 파일과 `mkdocs.yml`이 사이트의 재료다.
2. `main` 브랜치에 push하면 GitHub Actions(`.github/workflows/deploy.yml`)가 실행된다.
3. Actions는 LaTeX와 MkDocs를 설치한 뒤 `mkdocs build --strict`로 사이트를 만든다. 이때 `hooks/`의 변환기가 TikZ 그림을 변환한다.
4. 빌드가 성공한 경우에만 GitHub Pages에 게시된다. 실패하면 직전에 성공한 사이트가 그대로 남는다.

- 내용을 바꾸려면 `docs/` 안의 파일을 고친다.
- 사이트의 모양과 기능을 바꾸려면 `mkdocs.yml`을 고친다.
- `site/`와 `.cache/`는 빌드할 때 자동으로 생기는 폴더다. 고치지 않고 커밋하지 않는다.

## 3. 저장소 구조와 공개 범위

| 위치 | 용도 | 공개 |
|---|---|---|
| `docs/<대분류>/` | 노트 페이지 | 사이트에 공개 |
| `docs/code/<언어>/` | 구현 코드 파일 | 사이트에 공개 (내려받기 가능) |
| `docs/references/` | 재배포가 허가된 참고자료 파일 | 사이트에 공개 (내려받기 가능) |
| `docs/stylesheets/`, `docs/javascripts/` | 사이트 디자인과 수식 표시 | 사이트에 공개 |
| `templates/` | 페이지 템플릿 | 저장소에서만 보임 |
| `hooks/` | TikZ 변환기 | 저장소에서만 보임 |
| `.github/workflows/` | 자동 빌드·배포 설정 | 저장소에서만 보임 |

**공개 범위 규칙**

- `docs/` 안의 파일은 종류와 관계없이 모두 사이트에 공개된다. `nav`에 등록하지 않은 페이지도 공개된다.
- 예외적으로 `__pycache__/`, `*.pyc`, `.DS_Store`만 사이트에서 제외된다 (`mkdocs.yml`의 `exclude_docs`). 그 밖의 부산물(빌드 결과물, 가상환경 등)은 `docs/` 안에 만들지 않는다.
- 저장소가 공개이므로 `docs/` 밖의 파일도 GitHub에서 누구나 볼 수 있다.
- Git은 삭제한 파일도 기록에 남긴다. 공개하면 안 되는 파일은 잠깐이라도 커밋하지 않는다.
- `docs/javascripts/`와 `docs/stylesheets/`는 `mkdocs.yml`이 경로로 참조한다. 옮기거나 이름을 바꾸지 않는다.
- `docs/code/.gitkeep`은 빈 `code` 폴더를 Git에 유지하기 위한 파일이다. 지우지 않는다.

## 4. 항목 배치 규칙

### 4.1 대분류

| 폴더 | 분야 |
|---|---|
| `mathematics/` | 수학 |
| `cryptography/` | 암호학 |
| `computer-science/` | 컴퓨터 과학 이론 (알고리즘, 자료구조, 계산 이론 등) |
| `computer-systems/` | 컴퓨터 시스템 (컴퓨터 구조, 운영체제, 병렬 컴퓨팅, 네트워크 등) |
| `programming/` | 프로그래밍 언어·도구·구현 기법, 실제 구현 코드 |
| `projects/` | 개인 프로젝트 |

- 페이지는 `docs/<대분류>/<소분류>/<항목>.md`에 둔다 (3단계).
- 프로젝트 페이지는 `docs/projects/<프로젝트>.md`에 둔다.
- 새 대분류는 기존 대분류 어디에도 속하지 않는 분야를 공부하게 되었을 때만 추가한다.

### 4.2 배치 판별 기준

어디에 둘지 애매하면 아래 순서대로 판단한다.

1. **대상:** 이 내용이 *무엇에 대한* 지식인지로 정한다. 어떤 계기로 배웠는지는 기준이 아니다.
2. **추상 수준:** 어떤 기계나 환경에서도 성립하는 내용은 이론 분야(`mathematics/`, `cryptography/`, `computer-science/`)에 둔다. 특정 기계·언어·환경에 의존하는 내용은 `computer-systems/`나 `programming/`에 둔다.
3. **정본:** 여러 분야에 걸치면 가장 기초가 되는 분야에 정본을 쓰고, 나머지 분야에서는 정본으로 링크만 한다. 같은 내용을 두 곳에 쓰지 않는다.

### 4.3 이론과 구현의 분리

- 알고리즘의 절차(의사코드), 정확성, 복잡도는 해당 분야 개념 페이지 안의 알고리즘 상자에 쓴다.
- 실제 코드는 `docs/programming/<언어>/`의 구현 페이지에 쓴다. 같은 알고리즘을 여러 언어로 구현하면 언어마다 구현 페이지를 따로 만든다.
- 알고리즘 상자와 구현 페이지는 서로를 링크한다 (6.4절).

## 5. 파일·폴더 이름 규칙

- 페이지(`.md`), 폴더, 참고자료 파일의 이름은 영문 소문자, 숫자, 하이픈(`-`)만 쓴다.
- 코드 파일의 이름은 그 언어의 관례를 따른다. 하이픈이 허용되지 않는 언어에서는 밑줄(`_`)을 쓴다.
- 대소문자를 섞지 않는다. GitHub는 대소문자를 구분하므로, 대소문자만 달라도 다른 파일로 취급된다.
- 파일 경로가 곧 사이트 주소다. 한 번 정한 이름은 바꾸지 않는다.
- 이름을 바꾸거나 파일을 옮겨야 한다면, 그 파일을 가리키는 모든 링크를 함께 고친다. 고치지 않은 링크는 빌드가 목록으로 알려준다 **(빌드 검사)**. 여러 곳을 한 번에 고칠 때는 편집기의 "폴더 전체에서 찾아 바꾸기"를 쓴다.
- 이름은 사이트 밖에서 이 페이지로 걸린 링크(북마크 등)까지 바꿀 수 없다. 그래서 바꾸지 않는 것이 원칙이다.

## 6. 페이지 유형과 공통 형식

### 6.1 유형과 템플릿

| 유형 | 템플릿 | 위치 |
|---|---|---|
| 개념 페이지 (이론 항목) | `templates/concept.md` | `docs/<대분류>/<소분류>/` |
| 구현 페이지 (실제 코드) | `templates/implementation.md` | `docs/programming/<언어>/` |
| 프로젝트 페이지 | `templates/project.md` | `docs/projects/` |
| 하드웨어 페이지 | `templates/hardware.md` | `docs/computer-systems/architecture/` |

- 템플릿은 `docs/` 밖에 둔다. 템플릿의 자리표시자는 일부러 빌드가 실패하도록 만들어져 있어서, `docs/` 안에 두면 빌드가 멈춘다.
- 템플릿 상단의 HTML 주석(`<!-- … -->`)은 화면에는 보이지 않지만 페이지 소스에는 남는다. 다 쓴 뒤에는 지운다.

### 6.2 모든 페이지의 공통 형식

1. 첫 줄은 제목이다: `# <한국어 이름> (<영어 이름>)`
2. 제목 바로 아래에 상태 줄을 둔다: `*상태: <작성 중 | 검증 완료> · 최종 수정일: <YYYY-MM-DD>*`
3. 헷갈릴 수 있는 표기가 있으면 상태 줄 다음에 표기 상자를 둔다 (7.3절).
4. 본문
5. 마지막 절은 `## 출처 (References)`이다 (9.4절).

### 6.3 유형별 필수 내용

- **개념 페이지:** 정의·정리·예·알고리즘 상자로 구성한다. 필요 없는 종류의 상자는 두지 않는다.
- **구현 페이지:** 구현 대상(알고리즘이 있는 개념 페이지로 링크), 기준 문서, 환경(언어와 버전, 의존성과 버전, 결과에 영향을 주는 실행 환경), 코드, 테스트 벡터와 그 출처, 한계와 주의점
- **프로젝트 페이지:** 목표, 개요(기간, 저장소, 사용 기술), 사용한 이론·구현(페이지 링크), 구조, 날짜별 진행 기록, 회고
- **하드웨어 페이지:** 기본 정보(제조사, 모델, 데이터시트의 문서 번호·개정 번호·날짜), 핵심 사양(값, 단위, 데이터시트 쪽수 근거), 동작 원리, 이 하드웨어를 쓰는 구현 페이지 링크

### 6.4 양방향 링크

- 알고리즘 상자의 `**구현.**` 줄에 그 알고리즘을 구현한 모든 구현 페이지를 링크한다.
- 구현 페이지의 "구현 대상"에는 알고리즘 상자가 있는 개념 페이지로 링크하고, 알고리즘 이름을 함께 적는다.
- 구현 페이지를 새로 만들거나 지우면, 대상 알고리즘 상자의 `**구현.**` 줄도 함께 고친다.

## 7. 상자

### 7.1 종류

| 상자 종류 | 제목 앞에 붙는 이름 |
|---|---|
| `definition` | 정의 |
| `theorem` | 정리, 보조정리, 명제, 따름정리 |
| `example` | 예, 반례 |
| `algorithm` | 알고리즘 |
| `note` | 표기 (또는 일반 참고) |
| `warning` | 주의 |

- 정리·보조정리·명제·따름정리는 모두 `theorem` 상자를 쓰고, 종류는 제목 앞 이름으로 구분한다.
- 예와 반례는 모두 `example` 상자를 쓴다.

### 7.2 형식

상자는 다음 형식으로 쓴다.

```text
/// <상자 종류> | <제목 앞 이름> · <한국어 이름> (<영어 이름>)

<내용>
///
```

- 상자 첫 줄 다음에 빈 줄을 하나 두고 내용을 쓴다.
- 한 페이지 안에서 같은 종류의 상자 이름이 겹치지 않게 짓는다. 다른 페이지에서 이 상자를 언급할 때 이름으로 가리키기 때문이다.
- 증명은 해당 정리 상자 안에 접이식 증명 상자로 넣는다. 안쪽 상자는 바깥 상자보다 `/`를 하나 더 많이 쓴다.

```text
//// proof | 증명
<증명 내용> $\blacksquare$
////
```

### 7.3 표기 상자

- 페이지 안에서 헷갈릴 수 있는 표기(분야마다 관례가 다른 기호, 포함 여부가 갈리는 정의 등)는 페이지 맨 위의 표기 상자에 밝힌다.
- 사이트 전체에 적용되는 표기 규약은 두지 않는다. 표기는 페이지마다 필요할 때 밝힌다.
- 표기 상자는 페이지에 하나만 둔다.

## 8. 링크 규칙

- 사이트 안의 링크는 현재 파일에서 대상 `.md` 파일까지의 상대 경로로 건다. 사이트 주소(URL)로 걸지 않는다.
- 다른 용어가 **그 페이지에서 처음 등장할 때** 그 용어를 정의한 페이지로 링크한다: `<상대 경로>.md`. 같은 페이지에 정의가 있으면 링크하지 않는다.
- 다른 정리·예·알고리즘을 언급할 때는 그것이 있는 페이지로 링크하고, 상자 제목의 이름을 함께 적는다.
- 링크는 페이지까지만 건다. 페이지 안의 특정 위치(`#…`)로 가는 링크는 쓰지 않는다.
- 대상 파일이 없으면 빌드가 실패한다 **(빌드 검사)**.
- 사이트 밖으로 나가는 링크는 빌드가 검사하지 않는다. 직접 확인한다.

## 9. 출처와 날짜

### 9.1 날짜

- 날짜는 항상 `YYYY-MM-DD` 형식으로 쓴다.
- 최종 수정일은 페이지 내용을 고칠 때마다 갱신한다.

### 9.2 각주

- 사실 주장에는 문장 끝에 각주(`[^<식별자>]`)를 단다.
- 식별자는 출처를 알아볼 수 있는 의미 있는 이름으로 짓는다. 순번은 쓰지 않는다.
- 한 페이지에서 같은 출처는 같은 식별자로 다시 인용한다.
- 시간에 따라 바뀔 수 있는 값(표준의 최신 버전, 권고값 등)은 그 문장의 각주에 확인일을 적는다.
- 직접 작성하거나 추론한 내용은 출처가 없다는 것과 작성일을 적은 각주를 단다.

### 9.3 출처 유형별 필수 항목

| 유형 | 필수 항목 |
|---|---|
| 책 | 저자, 제목, 판, 출판사, 출판 연도, 위치(쪽, 정리 번호 등) |
| 논문 | 저자, 제목, 게재지, 권·호, 연도, 쪽, DOI (있으면) |
| 표준·기관 문서 | 발행 기관, 문서 번호, 제목, 버전 또는 발행일, DOI 또는 URL, 접근일 |
| 웹 페이지 | 작성자 또는 기관, 제목, URL, 접근일 |
| 데이터시트 | 제조사, 제목, 문서 번호, 개정 번호, 발행일, URL, 접근일 |

- URL로 인용하는 모든 출처에는 접근일 `(accessed <YYYY-MM-DD>)`을 적는다. 웹 내용은 바뀔 수 있기 때문이다.

### 9.4 출처 절

- 페이지의 마지막 절 `## 출처 (References)`에 그 페이지가 참고한 문헌을 모두 모아 적는다.
- 각주 내용은 이 절 아래에 둔다. 사이트에서는 페이지 맨 아래에 자동으로 모아서 표시된다.

### 9.5 인용

- 기본은 원문을 자기 말로 다시 쓰고 출처 각주를 다는 것이다.
- 원문을 그대로 옮겨야 할 때만 인용 표시를 하고 짧게 옮긴다.

## 10. 작성 상태

- **작성 중:** 아래 기준을 아직 충족하지 못한 상태
- **검증 완료:** 모든 사실 주장에 출처 각주가 있고, 각 주장을 원문과 대조를 마친 상태
- (제안) 검증 완료 페이지의 내용을 고치면, 고친 부분을 원문과 다시 대조하기 전까지 상태를 작성 중으로 되돌린다.

## 11. 수식

- 문장 안의 수식은 `$ … $`, 따로 줄을 차지하는 수식은 `$$ … $$`로 쓴다.
- 수식은 방문자의 브라우저가 MathJax를 인터넷에서 받아와 그린다. 수식이 날것 그대로 보이면 네트워크나 스크립트 차단 문제다.

## 12. 그림 (TikZ)

### 12.1 작성

- 모든 그림은 TikZ로 작성한다. 코드 블록의 언어를 `tikz`로 지정하고, 안에 `tikzpicture` 환경이나 `tikzcd` 환경을 쓴다.
- 코드 블록 맨 위에 다음 지시 줄을 둘 수 있다.

| 지시 줄 | 뜻 | 필수 |
|---|---|---|
| `%alt: <설명>` | 그림의 대체 텍스트 | 권장 |
| `%preamble: <LaTeX 코드>` | 이 그림에만 추가할 패키지·라이브러리 | 선택 |
| `%scale: <숫자>` | 화면 표시 배율 (기본 1.3). 표시 크기만 바뀌고 그림 자체는 바뀌지 않음 | 선택 |

- 모든 그림에 공통으로 들어가는 패키지: `kotex`(한글), `amsmath`, `amssymb`, `amsthm`, `tikz`, `tikz-cd`, `pgfplots`, 그리고 자주 쓰는 TikZ 라이브러리. 목록은 `hooks/tikz.py`의 `BASE_PREAMBLE`에 있다.
- 그림은 상자 안(정의·정리·증명 등)에도 넣을 수 있다.
- 페이지에서 TikZ 문법 자체를 보여주려면, 그 코드 블록을 더 많은 백틱으로 된 코드 블록으로 감싼다. 그러면 변환하지 않는다.

### 12.2 변환과 오류

- 빌드할 때 LaTeX로 컴파일해 SVG로 바꾸고, 이미지로 페이지에 넣는다. 글자는 도형으로 바뀌므로 방문자의 글꼴과 관계없이 똑같이 보인다.
- 다크 모드에서는 그림의 색을 반전해서 표시한다.
- 변환한 그림은 `.cache/tikz/`에 저장했다가 다음 빌드에서 재사용한다. 코드가 바뀐 그림만 다시 컴파일한다.
- 컴파일에 실패하면 빌드가 멈추고, 페이지 이름과 LaTeX 오류를 알려준다 **(빌드 검사)**. 오류에 나오는 줄 번호는 `.md` 파일이 아니라 변환기가 만든 LaTeX 문서의 줄 번호다. 틀린 곳은 오류에 나온 명령 이름으로 찾는다.
- 내 컴퓨터에서 그림이 있는 페이지를 미리 보려면 LaTeX 배포판(MacTeX 등)이 설치되어 있어야 한다.

---

## 13. 코드

- 구현 코드는 `docs/code/<언어>/`에 실제 파일로 둔다. `.md` 안에 코드를 직접 붙여 넣지 않는다. 그래야 실행하는 코드와 페이지에 보이는 코드가 항상 같다.
- 구현 페이지에서는 코드 블록 안에 `--8<-- "<언어>/<파일>"` 한 줄로 불러온다. 경로는 `docs/code/` 기준이다.
- `docs/code/` 밖의 파일은 불러올 수 없다 **(빌드 검사)**.
- 불러올 파일이 없으면 빌드가 실패한다 **(빌드 검사)**.
- 코드 파일은 내려받을 수 있게 공개된다. 구현 페이지에 코드 파일로 가는 상대 경로 링크를 둔다.
- `--8<--` 줄은 코드 블록 안에 있어도 파일을 불러온다. 페이지에서 이 문법 자체를 보여주려면 줄 맨 앞에 `;`를 붙인다.

---

## 14. 참고자료 파일

- 재배포가 허가된 파일만 `docs/references/`에 둔다. 허가 여부가 확실하지 않으면 올리지 않고, DOI나 URL로만 인용한다.
- 파일은 사이트에 공개되어 누구나 내려받을 수 있다.
- 페이지에서는 상대 경로로 링크한다. 링크한 파일이 없으면 빌드가 실패한다 **(빌드 검사)**.
- 페이지 안에 PDF를 직접 띄우려면 `<iframe class="pdf-embed" src="<상대 경로>"></iframe>`을 쓴다. 파일이 크면 링크로 대신한다.

## 15. 새 페이지 작성 절차

1. 4절의 기준으로 위치를 정하고, 6.1절의 템플릿을 복사해 `docs/` 아래에 둔다.
2. 제목, 상태 줄, 최종 수정일을 채운다.
3. 내용을 쓰고, 각 사실 주장에 출처 각주를 단다.
4. 다른 용어가 처음 나오는 곳에 그 용어를 정의한 페이지로 링크를 건다.
5. 구현 페이지라면 코드 파일을 `docs/code/<언어>/`에 두고, 대상 알고리즘 상자의 `**구현.**` 줄을 고친다.
6. `mkdocs.yml`의 `nav`에 페이지를 추가하고, 해당 구역 개요 페이지(`index.md`)의 항목 목록에도 추가한다. `nav`에 없으면 사이드바에 나타나지 않는다. 다만 공개는 된다.
7. 템플릿 주석을 지운다.
8. commit하고 push한 뒤, Actions 탭에서 빌드가 성공했는지 확인한다.

## 16. 빌드와 배포

### 16.1 확인 순서

- 사이트가 바뀌지 않으면 먼저 Actions 탭을 본다.
  - 실패했다면 빌드 로그의 `ERROR`와 `WARNING` 줄을 읽고 지목된 곳을 고친다.
  - 성공했는데 화면이 그대로라면 브라우저 캐시 문제다. 강력 새로고침을 한다.
  - 실행 기록이 없다면 push가 되지 않은 것이다.

### 16.2 빌드가 실패하는 주요 원인

- 링크한 파일이 없음 (이름 변경, 이동, 대소문자 불일치, 오타)
- `nav`에 적은 파일이 없음
- 불러올 코드 파일이 없음
- TikZ 컴파일 오류
- `mkdocs.yml` 들여쓰기 오류

### 16.3 내 컴퓨터에서 미리 보기

- `pip install -r requirements.txt`로 설치하고, `mkdocs serve`로 미리 보거나 `mkdocs build --strict`로 배포와 같은 조건에서 검사한다.
- TikZ 그림이 있는 페이지는 LaTeX 배포판이 필요하다 (12.2절).

---

## 17. 의존성 관리

- `requirements.txt`에 MkDocs와 Material 테마의 버전을 고정한다. 버전을 올릴 때는 빌드가 성공하는지 확인한다.
- MkDocs 2.x로 올리지 않는다. TikZ 변환기가 쓰는 hooks 기능이 2.x에서 동작하지 않을 수 있다.
- Dependabot이 보낸 버전 업데이트 요청은 병합하기 전에 무엇을 올리는지 확인한다. 병합 즉시 `main`에 push되어 배포가 실행된다.

## 18. 파일별 역할

### 18.1 `mkdocs.yml`

| 항목 | 역할 | 주의 |
|---|---|---|
| `site_name` | 사이트 제목 | |
| `site_url` | 사이트 주소 | 실제 배포 주소와 같아야 한다 |
| `repo_url`, `repo_name` | 오른쪽 위 저장소 링크 | `repo_url`은 계정이 아니라 저장소 주소여야 한다 |
| `edit_uri` | 각 페이지의 편집 버튼 경로 | `repo_url`에 이어 붙는다 |
| `extra.generator` | 하단 제작 도구 문구 표시 여부 | `theme`가 아니라 `extra` 아래에 둔다 |
| `hooks` | TikZ 변환기 등록 | |
| `markdown_extensions` | 수식, 각주, 상자, 코드 불러오기 등 | `pymdownx.snippets`의 `base_path`, `restrict_base_path`, `check_paths`를 바꾸지 않는다 |
| `exclude_docs` | 사이트에서 제외할 파일 | |
| `validation.anchors` | 페이지 안의 없는 위치(`#…`)로 건 링크를 경고로 처리 | `warn`을 유지한다. 기본값에서는 검사하지 않는다 |
| `nav` | 사이드바 구성과 순서 | |

### 18.2 그 밖의 파일

| 파일 | 역할 |
|---|---|
| `.github/workflows/deploy.yml` | push되면 LaTeX 설치, 그림 캐시 복원, MkDocs 설치, 빌드, 게시를 실행 |
| `requirements.txt` | 설치할 MkDocs와 테마의 버전 |
| `.gitignore` | 커밋하지 않을 파일 (`.DS_Store`, `site/`, `.venv/`, `__pycache__/`, `*.pyc`, `.cache/`) |
| `hooks/tikz.py` | TikZ → SVG 변환. `BASE_PREAMBLE`(공통 패키지), `DEFAULT_SCALE`(기본 배율) |
| `docs/stylesheets/extra.css` | 본문 글꼴, 상자 색·아이콘, 그림 정렬, 다크 모드 처리 |
| `docs/javascripts/mathjax.js` | 수식 표시 설정 |
